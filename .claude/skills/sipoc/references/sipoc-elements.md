# SIPOC Elements Reference

Domain knowledge for SIPOC process mapping — element definitions, classification patterns, transformation types, handoff types, variance handling, and quality criteria.

---

## Core SIPOC Elements

### Suppliers (S)

The entities that provide inputs to a process step.

| Category | Description | Examples |
|----------|-------------|----------|
| Internal Department | Team or function within the organization | Finance, IT, Warehouse, HR |
| External Vendor | Third-party company or contractor | Logistics provider, SaaS vendor, raw material supplier |
| System / Application | Software that generates or delivers data | ERP, CRM, API endpoint, database |
| Customer / End-User | When the customer provides information or materials | Customer order form, uploaded documents |
| Regulatory Body | Government or standards organization | ATO, APRA, ISO certification body |

**Extraction cues**: Look for "provided by", "comes from", "sourced from", "received from", "submitted by", "generated by".

### Inputs (I)

The materials, data, or information consumed by a process step.

| Category | Description | Examples |
|----------|-------------|----------|
| Data / Information | Structured or unstructured data | Order CSV, customer record, specification doc |
| Physical Material | Tangible goods or components | Raw materials, packaging, hardware |
| Document / Form | Templates, approvals, or reference docs | Purchase order, approval form, SLA |
| Decision / Authorization | Sign-off or approval gate | Manager approval, budget authorization |
| Trigger / Event | Condition that initiates the process | Schedule trigger, threshold alert, customer request |

**Extraction cues**: Look for "requires", "needs", "takes in", "receives", "based on", "using".

### Process (P)

The sequence of activities that transform inputs into outputs.

| Level | Scope | Naming Convention | Example |
|-------|-------|-------------------|---------|
| L1 | End-to-end process | Verb + noun phrase | "Manage Product Hierarchy Changes" |
| L2 | Sub-process / phase | Verb + noun phrase | "Validate Change Request" |
| L3 | Task / activity | Verb + specific object | "Compare proposed SKU against master list" |

**Naming rules**:
- Always start with an **action verb** (Receive, Validate, Transform, Route, Approve, Generate, Distribute)
- Use client's terminology for nouns — never substitute generic terms
- Keep L1 names broad, L2 names scoped, L3 names specific and testable

### Outputs (O)

The results, products, or deliverables produced by a process step.

| Category | Description | Examples |
|----------|-------------|----------|
| Data / Record | Created or updated data | Updated customer record, generated report |
| Physical Product | Tangible deliverable | Assembled unit, packaged shipment |
| Document / Report | Formal output document | Invoice, compliance report, dashboard |
| Decision / Status | Outcome of evaluation | Approved/Rejected status, risk rating |
| Notification / Signal | Communication or trigger for next step | Email confirmation, webhook, status update |

**Extraction cues**: Look for "produces", "generates", "results in", "delivers", "creates", "updates".

### Customers (C)

The recipients or consumers of the outputs.

| Category | Description | Examples |
|----------|-------------|----------|
| Internal Stakeholder | Person or team consuming the output | Operations manager, compliance team |
| External Customer | End customer or client | Retail buyer, API consumer |
| Downstream Process | Next process in the chain | Shipping process, billing cycle |
| System / Database | System that receives the output | Data warehouse, reporting dashboard |
| Regulator / Auditor | Entity requiring the output for compliance | Tax authority, external auditor |

**Extraction cues**: Look for "goes to", "received by", "consumed by", "used by", "for the benefit of", "handed to".

## Transformation Types

Transformations describe **what changes** between input and output at each process step. Every process step MUST have at least one transformation identified.

| Type | Code | Description | Example |
|------|------|-------------|---------|
| Format Conversion | `FMT` | Data changes representation | CSV to JSON, paper to digital |
| Aggregation | `AGG` | Multiple items combined | Line items summed to order total |
| Enrichment | `ENR` | Additional data appended | Customer record + credit score lookup |
| Validation | `VAL` | Data checked against rules | Order checked against inventory levels |
| Filtering | `FLT` | Subset selected from larger set | Active customers extracted from full list |
| Calculation | `CAL` | New values derived | Unit price x quantity = line total |
| Status Change | `STS` | State transition | Order: "Pending" to "Approved" |
| Routing | `RTE` | Direction determined | High-value orders routed to senior approver |
| Decomposition | `DEC` | Single item split into parts | Purchase order split into warehouse picks |
| Assembly | `ASM` | Parts combined into whole | Components assembled into finished product |
| Authorization | `AUT` | Approval or sign-off applied | Manager sign-off added to expense claim |
| Notification | `NTF` | Stakeholders informed | Confirmation email sent to customer |

**Transformation chain**: The end-to-end sequence of transformations from first input to final output. Document as: `Input → [FMT] → [VAL] → [ENR] → [CAL] → Output`

## Handoff Types

Handoffs describe the **linkage between process steps** — how outputs from one step become inputs to the next.

| Type | Code | Description | Risk Level |
|------|------|-------------|------------|
| Direct Pass | `DIR` | Output flows directly to next step, no intermediary | Low |
| Queue / Buffer | `QUE` | Output placed in queue for async pickup | Medium |
| System Integration | `SYS` | Automated transfer via API, ETL, or messaging | Medium |
| Manual Handoff | `MAN` | Human transfers output (email, verbal, physical) | High |
| Shared Repository | `REP` | Output stored in shared location for pickup | Medium |
| Approval Gate | `GAT` | Output held pending authorization before proceeding | High |
| Broadcast | `BRC` | Output distributed to multiple recipients simultaneously | Medium |
| Callback / Webhook | `CBK` | Next step triggered by event notification | Low |

**Handoff documentation** (for each handoff, capture):
1. **From**: Source process step + role
2. **To**: Target process step + role
3. **Mechanism**: How the transfer happens (email, API, shared drive, etc.)
4. **SLA**: Expected transfer time
5. **Verification**: How the recipient confirms receipt
6. **Failure mode**: What happens if handoff fails

## Variance Classification

Variances are deviations from the normal ("happy path") process flow. Each variance is treated as a **first-class sub-SIPOC chain**.

### Variance Categories

| Category | Code | Description | Example |
|----------|------|-------------|---------|
| Exception | `EXC` | Error or unexpected condition | Invalid data format, missing field |
| Rejection | `REJ` | Item fails validation or approval | Order rejected for insufficient credit |
| Escalation | `ESC` | Item requires higher authority | Value exceeds approval threshold |
| Rework | `RWK` | Item returned to earlier step for correction | Form returned for missing information |
| Branching | `BRN` | Alternate path based on business rule | International vs domestic shipping |
| Timeout | `TMO` | Step exceeds time limit | Approval not received within 48 hours |
| Cancellation | `CAN` | Process terminated before completion | Customer cancels order mid-processing |

### Variance Documentation Template

For each variance, capture:

```
**Variance ID**: V-{parent_step}-{sequence}
**Parent Step**: {process step where variance originates}
**Category**: {EXC|REJ|ESC|RWK|BRN|TMO|CAN}
**Trigger**: {condition that causes the deviation}
**Sub-SIPOC**:
  - Supplier: {who provides inputs to the variance handling}
  - Input: {what the variance handler receives}
  - Process: {steps to handle the variance}
  - Output: {result of variance handling}
  - Customer: {who receives the variance output}
**Rejoin Point**: {where variance merges back to main flow | "Terminal" | "Escalation"}
**Frequency**: {estimated occurrence rate}
**Impact**: {Low | Medium | High | Critical}
```

### Variance-to-Flow Rules

1. If a variance **rejoins** the main flow → dotted arrow back to the rejoin step
2. If a variance is **terminal** (process ends) → arrow to an end node
3. If a variance **escalates** → arrow to an escalation handler (separate subgraph)
4. If a variance triggers **rework** → arrow back to the originating step or earlier
5. Multiple variances from the same step → each gets its own sub-SIPOC chain

## Common SIPOC Patterns

### Pattern 1: Request-Fulfill

```
Customer → Request Form → Receive & Log → Validated Request → Fulfill → Deliverable → Customer
```

Common in: Service requests, procurement, IT tickets.

### Pattern 2: Create-Review-Approve

```
Author → Draft → Create Content → Draft Output → Review → Reviewed Content → Approve → Published → Stakeholders
```

Common in: Document management, change control, compliance.

### Pattern 3: Collect-Transform-Distribute

```
Sources → Raw Data → Collect & Validate → Clean Data → Transform & Enrich → Enriched Data → Distribute → Consumers
```

Common in: Data pipelines, reporting, ETL processes.

### Pattern 4: Monitor-Detect-Respond

```
Systems → Metrics/Logs → Monitor → Alerts → Detect & Triage → Incident Record → Respond & Resolve → Resolution → Stakeholders
```

Common in: Operations, security, quality control.

### Pattern 5: Plan-Execute-Control

```
Stakeholders → Requirements → Plan → Project Plan → Execute → Deliverables → Control & Report → Status Reports → Stakeholders
```

Common in: Project management, manufacturing, campaign execution.

## Quality Criteria

### Completeness Checks

| Check | Rule | Flag |
|-------|------|------|
| Every process step has at least one supplier | No orphan steps | `[NEEDED: Supplier for "{step}"]` |
| Every process step has at least one input | No empty inputs | `[NEEDED: Input for "{step}"]` |
| Every process step has at least one output | No dead-end steps | `[NEEDED: Output for "{step}"]` |
| Every process step has at least one customer | No unclaimed outputs | `[NEEDED: Customer for "{step}"]` |
| Every output maps to an input of a downstream step | Chain continuity | `[GAP: Output "{output}" has no downstream consumer]` |
| Every transformation is identified | No black-box steps | `[NEEDED: Transformation for "{step}"]` |
| Every handoff is documented | No invisible transfers | `[NEEDED: Handoff between "{step_a}" and "{step_b}"]` |
| All known variances are captured | Exception completeness | `[NEEDED: Variance handling for "{condition}"]` |

### Naming Conventions

- **Process steps**: Always `Verb + Noun Phrase` (e.g., "Validate Order Data")
- **Inputs/Outputs**: Always `Adjective + Noun` or `Noun Phrase` (e.g., "Validated Order", "Raw Customer Data")
- **Suppliers/Customers**: Always proper nouns or role titles (e.g., "Warehouse Team", "SAP System")
- **Transformations**: Always use the type codes from the transformation table above
- **Use client terminology** — never substitute generic terms for domain-specific language

### Anti-Patterns to Avoid

| Anti-Pattern | Problem | Fix |
|-------------|---------|-----|
| "Process Data" as a step name | Too vague — what processing? | Specify: "Validate Order Fields Against Schema" |
| Same entity as both Supplier and Customer | May indicate a loop or missing step | Add intermediate step or clarify the cycle |
| No variances documented | Unrealistic — every process has exceptions | Probe for at least: rejection, timeout, escalation |
| Output with no transformation | Step adds no value | Either identify the hidden transformation or merge with adjacent step |
| Handoff described as "automatic" | Hides complexity | Specify the mechanism: API call, file transfer, queue message |
