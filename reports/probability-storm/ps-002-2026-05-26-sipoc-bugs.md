## Decision A — Wrap `resend.emails.send()` in fetchWithTimeout-style abort logic?

**File:** `lib/mailer.ts:31-38`
**Failsafe row affected:** "Mailer THROWS on error (no silent fail)" — additive, not replacing.

### L1: Field Scan — 78%

**Category:** integration (Resend SDK is an external dependency)

**Viability — 85%**
- Pattern already in-house: `lib/fetch.ts` exports `fetchWithTimeout()` with 5-6s AbortController. CLAUDE.md failsafe map calls it out as the standard for "every external HTTP call."
- BUT the Resend SDK doesn't take a `fetch` you supply (v3 has limited custom-fetch support). Direct `AbortController` wrap is feasible by racing the `resend.emails.send()` promise against a `setTimeout` reject. Slightly less clean than `fetchWithTimeout` but functionally equivalent.
- Blast radius: tiny — `lib/mailer.ts` is the single send point. Two callers (webhook route + admin reminder/review fallback routes).

**Strategic fit — 90%**
- CLAUDE.md failsafe map: "fetchWithTimeout() on every external HTTP call" — Resend SDK is currently the only external HTTP call *not* covered. This is a documented gap, not a policy change.
- ADR-001: Resend already throws on failure; mailer re-throws. Adding a timeout reinforces the throw-and-catch contract; doesn't conflict with ADR-001's "deeper Resend lock-in" tradeoff because the wrapper is local.
- SIPOC variance V-10-1 explicitly flags `[ASSUMED: Resend API response time <2s — no timeout configured on resend.emails.send() call itself]`. This fix retires the assumption.

**Cost-of-action — Low**
- ~10-line change in `lib/mailer.ts`: race `resend.emails.send(...)` against `new Promise((_, r) => setTimeout(() => r(new Error('Resend timeout')), 6000))`.
- One new unit test (mock SDK with a hanging promise; expect throw within 6s).
- No env-var, no infra, no migration.

**Cost-of-inaction — Medium**
- A hung Resend connection (their issue, network blip, DNS) holds the webhook handler open. Vercel function timeout is 10s on Hobby / 60s on Pro; webhook handler today does TWO sends sequentially → up to 20s in-flight if both hang. FareHarbor sees timeout → retries → potentially duplicate scheduled emails before the original fails.
- Compounds with Decision B: a hung send makes the "should we return 5xx?" question moot because the handler never finishes responding.

**Reversibility — Very High**
- Pure additive code. Revertible in one commit. No data migration, no schema, no env. Worst case: timeout is too tight → bump from 6s to 10s.

**Score: 78%** (base 60 + specificity +20 [file:line + named pattern] + severity +10 [cascade risk] + integration -5 + category risk -5 [integration] − no duplicate penalty − no saturation)

## Decision B — Webhook returns 200 even when both Resend schedules fail. Switch to 5xx, or stay 200 + add owner alert?

**File:** `app/api/fareharbor-webhook/route.ts:111-167`
**Failsafe row affected:** None directly; touches ADR-001 and ADR-003 boundaries.

### L1: Field Scan — 70%

**Category:** integration (FareHarbor webhook + Resend; cross-system retry contract)

**Viability — 75%**
- Code is already structured for it: both schedule calls are wrapped in `try/catch` with `console.error`. A boolean tracking either failure is trivial. Returning 5xx is one branch.
- The "alert owner" alternative is harder: no SendGrid/Resend-to-owner pipeline exists today for app-error notifications (only customer emails). Building it = new code path + new failure mode (what if the alert email also fails?).
- BUT — and this is the load-bearing concern — FareHarbor retries are NOT idempotent on our side. We don't dedupe by booking PK on retry. A 5xx response triggers FareHarbor to redeliver, and the second delivery re-runs `extractBooking → schedule TWO new emails → overwrite store entry`. The OLD email IDs (if scheduling partially succeeded) get orphaned in Resend's queue. That's a worse failure than the original bug.

**Strategic fit — 60%**
- ADR-003 says FareHarbor retries are acceptable at low volume ("accumulated retries fire in bulk once the var is set"). That ADR's "retry is OK" stance is about secret-unset 503s, not application-level failures. Reusing the retry channel for app errors is a stretch of ADR-003's contract.
- ADR-001 explicitly says "Resend handles retries on transient network failures natively." Returning 5xx adds a SECOND retry layer (FareHarbor → us → Resend) which can compound.
- Hybrid (return 200 + alert owner) preserves the FareHarbor handshake but loses the auto-retry property.

**Cost-of-action**
- **Return 5xx variant**: Low code cost (~5 lines), HIGH semantic cost (need dedupe in webhook to safely retry, which means hitting `bookingScheduleStore` for prior IDs and cancelling them on re-entry — touches ADR-001's in-memory store, which loses state on cold start; the retry might hit a different Vercel instance and orphan emails).
- **Stay 200 + owner alert variant**: Medium code cost (need a new "alert owner" pathway — could reuse existing owner-digest skeleton in `app/api/owner-digest/`, but the failsafe map doesn't currently list it). LOW semantic cost — single direction, no retry compounding.

**Cost-of-inaction — Medium**
- Today's failure mode: both emails fail → store gets `{reminderEmailId: null, reviewEmailId: null}` → guest gets no reminder, no review request → owner doesn't know. SIPOC variance V-10-1 marks impact as "Medium (guest misses reminder or review request; no operational impact)" — but "no operational impact" depends on the owner noticing the gap manually.
- Frequency assumed `<1%` in V-10-1. With Decision A unfixed, frequency creeps up (timeouts compound).

**Reversibility — Medium**
- Return-5xx is reversible code-wise BUT not behavior-wise: FareHarbor retries that already fired during the bug window may re-arrive in a queue. Rolling back doesn't un-deliver them.
- Owner-alert is fully additive and revertible.

**Score: 70%** (base 60 + specificity +15 [file:line + named pathway] + severity +10 [silent failure, no visibility] − integration ×2 −10 [FareHarbor + Resend + store] − category risk −5)
