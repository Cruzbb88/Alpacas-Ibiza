# Completeness Audit — ca-001-2026-05-27

Date: 2026-05-27  
Auditor: Claude Code (Sonnet 4.6), read-only static analysis  
Scope: routes, components, lib, data, specs, ADRs, CLAUDE.md failsafe map

---

## Verdict

**Mostly built, poorly tracked.** The core product surface is shippable: 55 routes exist, 20 API endpoints are covered, the integration/payment layer has real adapters with fail-safe guards, and the lib layer has solid unit-test coverage on security-critical modules. The spec registry is a lie — spec 003 (adopt page) and spec 004 (dead route deletion) are misclassified. Adopt is built and in TODO. Dead routes are in DONE but not deleted. 59 of 60 custom components have zero tests. Legal content (spec 002, still in TODO) consists of generic boilerplate — no CIF number, no actual GDPR data controller details, no real retention periods — which is a legal liability for an EU business before public launch. CLAUDE.md says "9 ADRs" but 18 exist; the count is stale by 9.

## Top 3 Biggest Gaps

**1. Legal content is placeholder (spec-002, TODO, P0)**  
`/privacy`, `/terms`, `/cookies` pages exist and render. The translations contain generic summaries ("We use cookies to improve your experience", "Last updated: February 2024") with no CIF number, no named data controller, no actual retention periods, no specific cookie table, no refund/cancellation policy matching FareHarbor flow settings. An EU-registered business showing this content to real users is a GDPR liability on launch day. The component infrastructure is ready; what's missing is owner-supplied legal text.

**2. Dead non-locale routes still live in repo (spec-004, DONE, P0 — falsely closed)**  
`app/about/page.tsx`, `app/contact/page.tsx`, `app/shop/*` are present and serving content (USD prices, invented team names). Spec-004 acceptance criteria require deletion; the spec is marked done. This is a spec-tracker lie. If Next.js route resolution resolves these before the `[locale]` catch-all (possible under certain middleware configs), real users get wrong pricing data.

**3. 59 of 60 custom components have zero tests**  
The lib layer is reasonably tested (35/52 modules). The component layer is not. Forms (`contact-form`, `commission-form`, `newsletter-form`), booking UI (`booking/button`, `booking/sticky-booking-bar`), and payment-adjacent UI (`billing-portal-link`, `adopt-thank-you`) all have zero automated coverage. Regressions in these are invisible until a human clicks through.

## Top 3 Overshipped Items (Built Without Spec)

**1. 27 locale pages with no spec**  
Routes like `/sustainability`, `/press-kit`, `/workshops`, `/yoga`, `/weddings`, `/offline`, `/sitemap`, `/media`, `/gifts` were all built without any spec. Their acceptance criteria, owner-fillable content requirements, and SEO obligations were never written down. Some of these have failsafe entries in CLAUDE.md; most do not.

**2. Full Mollie payment stack (no spec, partially covered by ADR-015)**  
ADR-015 deferred Mollie. A full Mollie adapter, checkout route, webhook route, payment handlers, and e2e tests were built anyway. This is good engineering but was done without a spec — ADR-015 became the de-facto spec post-hoc.

**3. `lib/data/press.ts`, `lib/data/awards.ts`, `lib/data/search-index.ts`**  
These data files were built and the components that render them (`press-logos.tsx`, `awards-badges.tsx`) are live, but no spec was written for what content they should contain, what the acceptance criteria are, or who owns the data. They're owner-fillable stubs with no documented data-collection request in OWNER_INPUT_NEEDED.md.

## CAN'T DO WITHOUT HELP

- **Runtime verification of privacy/legal content quality** — whether the translation strings constitute legally compliant GDPR policy text requires a lawyer or the owner reviewing against Spanish/EU requirements. Static analysis confirms structure exists; compliance is a human call.
- **Playwright e2e pass/fail** — e2e tests for booking redirect, contact form, and adopt checkout exist but require a running dev server. Whether they pass is unknown from static analysis.
- **Dead-route resolution order** — whether `app/about` actually serves before `[locale]/about` under the current middleware config requires a running app + network test.
- **Locale completeness for IT/FR** — whether the Italian and French translation files (spec-005 gap) are machine-guessed or genuinely empty requires reading all translation JSON files and comparing key coverage, which was out of scope here.
