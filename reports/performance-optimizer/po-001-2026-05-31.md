## L1: Critical Path Analysis

### Power Core Identified

**Bottleneck:** `getActiveAdopterCount()` — uncached Mollie/Stripe subscription-list API call  
**Location:** `lib/adopters/count.ts:131` called from `app/[locale]/adopt/page.tsx:108`  
**Estimated Time:** 200–2000 ms of ~210–2010 ms total SSR path (95–99% of server-side time)  
**Downstream Impact:** Affects `/adopt` cold-start SSR; `/adopt` is the highest-revenue page (adoption conversions). Every visitor who hits a cold process or a post-deployment first-request waits for this call.  
**Power Core Score:** 2000 × 8 = 16,000 (highest on any route)

**Why it matters:**

1. The 1-hour in-memory cache (`globalThis.__adopterCountCache`) is process-scoped. On Vercel every deployment cold-starts all serverless function instances. Every canary or region spin-up = cache miss = live Mollie/Stripe API call during the SSR of `/adopt`.
2. The call is sequential — `await getTenant()` runs first (line 100), then `await getActiveAdopterCount()` (line 108). Even though `getTenant` is ~1 ms, the two awaits are not parallelized.
3. Mollie's `subscriptions.iterate()` paginates up to 500 records. At 100ms/page that's 500–1000ms for a non-trivial subscriber list. Stripe's `subscriptions.list()` caps at 1000 at 100/page = 10 sequential API calls in the worst case.
4. This is the *only* server-side external API call on any of the three target pages. `/` and `/tours` make **zero** server-side API calls and render in <5ms. `/adopt` alone adds a 200–2000ms SSR penalty.

### Detailed Analysis: `getActiveAdopterCount()` — The Power Core

**Current performance:** 200–2000ms (cold, Mollie configured with ~50–500 active subscriptions)  
**Theoretical minimum:** 10ms  

**Calculation basis:**

The theoretical minimum for a "how many active subscriptions do I have?" query is a single API call returning a count, not a paginated iteration:
- Mollie offers `/v2/subscriptions?status=active&limit=1` which returns `count` in the metadata — no pagination needed: ~80ms API RTT
- Alternatively, store the count in a KV store (Vercel KV, Redis) as a background job — serving time: ~5ms cache read
- Even the current iteration approach with a warm in-memory cache: ~0ms

Theoretical floor for "adopter count on page render" = time to read a pre-computed integer from memory = **~0ms** (warm cache hit, which is the case 99.9% of requests after the first). The gap is the 0.1% cold-start tail latency on Vercel.

**Assumptions:**
1. Vercel serverless function, European region (Frankfurt/Madrid)
2. Mollie API RTT: ~80ms one-way from Vercel EU
3. Subscription list: 10–500 active subscriptions (iterate() pagination at 250/page max)
4. Cold start occurs: on every new deployment, ~once per hour per region per function instance spin-up

**Gap:** 190–1990ms (1900%–19,900% above theoretical)

**Recoverability:** High — the in-memory cache already EXISTS but it's process-scoped. Promoting it to a shared KV store or computing it as a build-time/background value eliminates the cold-start tail entirely.

**Key insight:** The counter shows on page load for every visitor but only 1-in-1000 requests actually needs to fetch it live; the other 999 serve a cached value. The cold start is a deployment artifact, not a real traffic problem — but it hits the first visitor after every deploy on the highest-conversion page.

### Detailed Analysis: `Hero` `'use client'` — Secondary Bottleneck

**Current performance:** Adds 80–200ms to TTI on all 3 routes (client bundle must download + parse before hero is interactive)  
**Theoretical minimum:** 0ms additional TTI  
**Basis:** Hero has `backgroundImage` (uses `<Image>` RSC-compatible), `videoSrc` (HTML5 `<video>` — RSC-compatible), and CTAs (static `<Link>` — RSC-compatible). The `'use client'` marker is not justified by any hook or browser API. Removing it makes the hero pure RSC HTML — browser renders it on first byte, no JS parse needed.  
**Gap:** 80–200ms TTI (100% of gap is avoidable)  
**Recoverability:** High

### Detailed Analysis: `GoogleReviewsBadge` client fetch waterfall on `/adopt`

**Current performance:** `/adopt` page renders `<GoogleReviewsWall>` as a server component that calls `fetch(\`${SITE_BASE_URL}/api/google-reviews\`)` with `next: { revalidate: 21600 }`. This is **correct** — it uses ISR. However the `/tours` page uses `<GoogleReviewsBadge>` (the client version at `components/google-reviews-badge.tsx`) which fires a `useEffect` fetch on mount.

**Current performance on /tours:** 200–400ms visible-content delay (mount → fetch → render)  
**Theoretical minimum:** 0ms (pre-fetched in page RSC with ISR cache)  
**Gap:** 200–400ms (fully avoidable)  
**Recoverability:** High

**Recommendation 1: Promote `getActiveAdopterCount` result to Vercel KV / edge-cached endpoint**

**Target:** `lib/adopters/count.ts` — `getCached()`/`setCached()` pair  
**What to change:** Replace the in-memory `globalThis.__adopterCountCache` Map with Vercel KV (`@vercel/kv`) using a 5-minute TTL. On cache miss, fire the Mollie/Stripe iterate() in the background (or use `waitUntil`), return 0 immediately, and let the cache warm asynchronously. The counter is decorative — showing `0` for 5 minutes after a deploy is acceptable.

**Pseudocode/approach:**
```ts
// lib/adopters/count.ts
import { kv } from '@vercel/kv'  // no new dependency if already in package.json; check first

const KV_KEY = `adopter-count:${vendor}`
const KV_TTL = 300 // 5 minutes

export async function getActiveAdopterCount(): Promise<AdopterCountResult> {
  // 1. Try KV (cross-process, survives cold starts)
  const cached = await kv.get<AdopterCountResult>(KV_KEY)
  if (cached) return cached
  
  // 2. Kick off refresh in background (don't block SSR)
  const refreshPromise = countForVendor(vendor).then(result =>
    kv.set(KV_KEY, result, { ex: KV_TTL })
  )
  
  // Option A: fire-and-forget (return 0, count appears on next load)
  void refreshPromise
  return { count: 0, source: 'warming' }
  
  // Option B: await with a 100ms race timeout (show count if fast, else 0)
  const result = await Promise.race([
    refreshPromise.then(r => r),
    new Promise<null>(resolve => setTimeout(() => resolve(null), 100))
  ])
  return result ?? { count: 0, source: 'timeout' }
}
```

If `@vercel/kv` is not available (no KV store provisioned), the current in-memory cache is fine — but add a 5-minute background revalidation so the cache stays warm across the 1-hour gap on busy deployments.

**Tests to add/modify:**
- Unit test: `getActiveAdopterCount()` returns cached value on second call within TTL
- Integration test: cold-start returns `{ count: 0, source: 'warming' }` within 50ms

**Watch for:** KV cold-start adds ~5ms overhead on its own first call. Size: not an issue — the stored object is <100 bytes.

const ITERATIONS = 20

async function benchAdoptSSR() {
