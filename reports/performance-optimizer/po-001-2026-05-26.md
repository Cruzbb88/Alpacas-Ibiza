## Route Analysis

### Route 1: `/` (Home)

#### Server-side cost
| Item | Cost |
|------|------|
| `params` await | ~1 ms (Next.js internal) |
| `t(locale)` — translations | Synchronous. All 6 locale JSONs are statically imported and held in memory. No I/O. Cold-start penalty only (~50–100 ms once, then free). |
| `localBusinessSchema()` + `organizationSchema()` | Pure computation, ~0 ms. |
| External fetches | NONE. Home page makes zero server-side API calls. |
| Structured data | 2 JSON-LD blobs emitted inline in `[locale]/layout.tsx`. Pure string, no I/O. |

**Server total: ~1–5 ms render time per request (near floor).**

#### Client-side cost
| Item | Cost |
|------|------|
| `Hero` component | `'use client'` with `trackConversion` import — forces hydration even though no interactive state exists on render. Imports `lucide-react/ArrowRight` + `@/lib/analytics`. |
| `ReviewCard` (x3) | `'use client'` — `useState` + `useEffect`. Each card has a translation-toggle. 3 hydration roots. |
| `NewsletterForm` | `'use client'` — form state + API call. Legitimate. |
| `StickyBookingBar` | `'use client'` — scroll listener + `useParams`. Renders in layout for every route. |
| `CookieConsent` | `'use client'` — local storage read + state. Layout-level. |
| `WeavingShowcase` | `'use client'` — no state or effects visible in component tree. Unnecessary boundary. |
| `ChoicePaths` | `'use client'` — static link grid. Unnecessary boundary. |
| `ExperienceCards` | `'use client'` — static card grid. Unnecessary boundary. |
| `Features` | `'use client'` — emoji + text list. Unnecessary boundary. |
| Fonts | Geist Sans + Playfair Display loaded via `next/font/google`. Both declared in root layout. Font requests are deferred to parallel download — no render-block post-demote. |
| GA4 gtag.js | `afterInteractive` — loads after hydration. No longer blocking. |
| FareHarbor API embed | `strategy="lazyOnload"` — loads after page is idle. Correct. |

**Critical-path bottleneck (Home):** `Hero` is `'use client'` and is the first component in the RSC tree. It forces the browser to download, parse, and execute the client bundle before the hero section can be interactive. Because it sits above the fold, this delays Time to Interactive for the most visible element. The hero has no client-only behavior — `trackConversion.bookTourClick()` is an onClick handler that could live in a thin `BookTourLink` wrapper (already extracted as `components/book-tour-link.tsx`, which is also `'use client'`). Hero itself could be a Server Component with a `BookTourLink` child.

**Estimated FCP gain from fix: ~100–200 ms** (reduces hydration payload for above-fold section; hero gradient renders from CSS without JS).

**Images:** Hero uses CSS `background-image` / gradient (no `<Image>`). No LCP image optimization possible until owner supplies a hero photo. When supplied, Hero must be refactored to use `<Image priority>` to gain LCP benefit.

#### Render-blocking resources
- `consent-default` inline script (`beforeInteractive`) — ~350 bytes, synchronous. Unavoidable per GDPR ordering. Negligible.
- Geist + Playfair font CSS — loaded by `next/font`, injected as preload link, non-blocking.

**Home FCP estimate: ~1.2–1.8 s (mobile P75)**
After Hero server-component refactor: **~1.0–1.4 s**

### Route 2: `/tours`

#### Server-side cost
| Item | Cost |
|------|------|
| `t(locale)` | Same as home — synchronous, in-memory. |
| `touristTripSchema()` | Pure computation. |
| `faqPageSchema(faqItems)` | Constructs 10-item FAQ schema — pure, ~0 ms. |
| External fetches | NONE server-side. Tours page makes zero server fetches. |
| Structured data | 2 JSON-LD blobs (TouristTrip + FAQPage) + 2 from layout (LocalBusiness + Organization) = 4 total inline scripts per page. |

**Server total: ~2–8 ms. No I/O bottleneck.**

#### Client-side cost
| Item | Cost |
|------|------|
| `Hero` | Same client boundary issue as home. |
| `FareHarborCalendar` | `'use client'` + `useEffect` + dynamic `<script>` injection to `fareharbor.com`. This is the single largest client-side fetch: FareHarbor calendar script loads third-party JS (~80–150 kB estimated) + makes its own API calls. **Cannot be optimized without replacing the embed model.** |
| `GoogleReviewsBadge` | `'use client'` + `useEffect` → `fetch('/api/google-reviews')` on mount. Client-to-server waterfall: hydrate → mount → fetch → render. ~200–400 ms added to visible content. |
| `AvailabilityUrgency` | `'use client'` + `useAvailability` hook → `fetch('/api/availability')` on mount. Another waterfall. API itself fans out to FareHarbor (1 items call + up to 3 availability calls, 5 s timeout each). |
| `ReviewCard` (x6) | `'use client'` — 6 hydration roots with useState/useEffect. |
| `FAQ` | `'use client'` — accordion state. Legitimate. |
| `CancellationBadge` | `'use client'` — check source needed but likely static. |
| `PageBreadcrumbs` | Likely server-capable. |

**Critical-path bottleneck (Tours):** The `GoogleReviewsBadge` + `AvailabilityUrgency` double fetch waterfall. Both fire on mount, both are visible in the booking section, and both gate user-facing content. The `AvailabilityUrgency` fetch triggers a server-side FareHarbor fan-out that can take 1–10 s. Meanwhile `FareHarborCalendar` injects a third-party script that itself makes additional calls. Tours is the only route with three independent client→server→external fetch chains firing simultaneously.

**3-step fix:**
1. Move `GoogleReviewsBadge` to a Server Component: `fetch('/api/google-reviews', { next: { revalidate: 3600 } })` in the Tours page server function, pass data as prop. Eliminates one client waterfall entirely.
2. Deduplicate `AvailabilityUrgency` fetch: use React context or SWR with a shared cache key so `booking-section.tsx` and `availability-urgency.tsx` don't double-fetch.
3. Set `NEXT_PUBLIC_FAREHARBOR_ITEM_ID` env var to skip the pre-flight items-list API call inside `/api/availability`. This removes one FareHarbor round-trip from the fan-out chain.

**Estimated FCP gain: ~0 ms** (FCP fires before booking section renders).
**Estimated TTI / booking-section paint gain: ~300–600 ms** (eliminates one full fetch waterfall, reduces FareHarbor chain from 2-step to 1-step).

**Tours LCP estimate: ~2.0–3.5 s (mobile P75, booking section visible)**
After fixes: **~1.4–2.0 s**

### Route 3: `/alpacas`

#### Server-side cost
| Item | Cost |
|------|------|
| `t(locale)` | Synchronous, in-memory. |
| `localBusinessSchema()` | Pure computation. |
| `ALPACAS` constant | 14-item static array import. Zero I/O. |
| `generateMetadata` | `await params` only — no fetches. |
| External fetches | NONE. Alpacas page is entirely static data. |

**Server total: ~1–3 ms. Absolute floor for this route is already nearly met on server side.**

#### Client-side cost
| Item | Cost |
|------|------|
| `Hero` | `'use client'` — same as all other routes. Unnecessary boundary for a gradient hero with no image. |
| `AlpacaCard` (x14) | Server Component. No `'use client'`. Uses `next/image` with correct `sizes` prop. **Currently all 14 images are `null`** — renders placeholder divs with text. Zero image I/O, zero LCP image cost. |
| Grid layout | Pure RSC rendering 14 static cards. No hydration overhead beyond Hero. |

**State: all 14 `image: null` fields mean the current page has ZERO real images.** The 14 placeholder divs are CSS-only. This is the lightest route in the codebase today.

**Critical-path bottleneck (Alpacas):** `Hero` as a `'use client'` component is still the only hydration cost. Once the 14 alpaca photos arrive from the owner, LCP will spike immediately unless `AlpacaCard` adds `priority` to the first-row images (4 cards at lg breakpoint). The `sizes` prop is already correctly set — this is the one component that did image work correctly.

**3-step fix (pre-emptive — before photos land):**
1. Convert `Hero` to Server Component (same fix as home/tours) — remove `'use client'`, extract onClick into `BookTourLink`.
2. Add `priority` prop to the first 4 `AlpacaCard` renders (above-fold at desktop) — pass `priority={index < 4}` from the page.
3. When photos land: add the CDN/storage hostname to `remotePatterns` in `next.config.mjs` before deploying.

**Estimated FCP gain: ~80–150 ms** (Hero hydration removed; page becomes near-100% SSR).

**Alpacas FCP estimate: ~0.9–1.4 s (mobile P75, current — no images)**
After Hero fix: **~0.7–1.0 s**
After real photos + priority: **~1.0–1.5 s** (LCP will shift to first image row; net neutral vs current if priority is set correctly)
