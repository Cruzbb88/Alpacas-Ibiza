## Part 2 — New a11y Findings (components added since 2026-05-27)

### N-01 — Mega-menu: `aria-expanded` value is a string, not boolean (WCAG 4.1.2) — MEDIUM
**File:** `components/header.tsx:410-412`
**Code:**
```tsx
aria-expanded={isMegaOpen ? 'true' : 'false'}
```
ARIA 1.1 specifies `aria-expanded` is a boolean attribute. React correctly serialises both the boolean `true` and the string `'true'` as `aria-expanded="true"` in the DOM, so this is not a functional failure — it will work in all current AT. However it is a deviation from ARIA best-practice and from how the mobile hamburger (line 528) correctly uses the string form consistently. The mega-menu trigger is a `<Link>` (not `<button>`), which does not have `aria-expanded` in its implicit ARIA role (links are role=link, not role=button). Placing `aria-haspopup="true"` + `aria-expanded` on a link is a mild role-mismatch that some AT may ignore.
**Fix:** Either change the trigger element from `<Link>` to `<button type="button">` (navigates on Enter, opens menu on Space/ArrowDown — APG combobox pattern), or accept current approach (link triggers navigation on Enter, menu opens on hover/focus — simpler, AT-tolerant). If keeping the link pattern, change `aria-haspopup="true"` to `aria-haspopup="menu"` for semantic accuracy.
**WCAG:** 4.1.2 Name, Role, Value

### N-02 — Mega-menu: focus does not advance into panel on keyboard (WCAG 2.1.1) — HIGH
**File:** `components/header.tsx:413`
**Code:**
```tsx
onFocus={() => setMegaOpen(item.slug)}
```
When a keyboard user tabs to a mega-menu trigger (e.g., "Experiences"), the panel opens (`setMegaOpen`), but focus remains on the trigger. The sub-links inside `mega-${item.slug}` are made reachable by removing `inert` (line 447: `inert={!isMegaOpen ? true : undefined}`), so Tab will advance into the panel naturally. However there is no managed focus or `ArrowDown` handler to deliberately move focus into the first menu item on open. The APG "Disclosure Navigation Menu" pattern requires that when the menu opens via keyboard, focus should either stay on the trigger (Tab advances into panel) or move to the first item. The current pattern works for Tab-navigation but does not implement arrow-key navigation expected by AT users familiar with APG menu patterns.
**Severity note:** This is a WCAG 2.1.1 (Keyboard) concern at the "substantially equivalent" threshold — keyboard users CAN reach all links, just not via ArrowDown. Mark as MEDIUM-HIGH.
**WCAG:** 2.1.1 Keyboard

### N-03 — GreetingCardPicker: `role="radio"` on `<button>` without `role="radiogroup"` wrapper (WCAG 1.3.1 / 4.1.2) — MEDIUM
**File:** `components/adopt/greeting-card-picker.tsx:74-79`
**Code:**
```tsx
<button
  type="button"
  role="radio"
  aria-checked={isSelected}
  aria-label={card.label}
```
The component correctly uses `<fieldset>` + `<legend>` and applies `role="radio"` + `aria-checked`. However the ARIA spec requires `role="radio"` elements to be owned by a `role="radiogroup"` container. The `.grid` `<div>` at line 70 has no `role="radiogroup"` attribute. Without the group, screen readers cannot announce the total count ("1 of 5") or navigate with Arrow keys between options.
**Fix:** Add `role="radiogroup"` to the grid `<div>` at line 70.
**WCAG:** 1.3.1 Info and Relationships, 4.1.2 Name, Role, Value

### N-04 — AlpacaPicker: "Pick for me" tile has no accessible state announcement for null selection (WCAG 4.1.2) — LOW
**File:** `components/adopt/alpaca-picker.tsx:85-98`

This is a LOW concern as individual `aria-label` on each tile is present.

### N-05 — Gift adoption form: no `id` on inputs; labels use wrapping pattern only (WCAG 1.3.1) — MEDIUM
**File:** `components/adopt/adopt-gift-adoption.tsx:169-195`
The gift adoption form wraps each `<input>` in a `<label>` (implicit association). This is a valid WCAG 1.3.1 technique (H44/H65 alternative). However the `<input>` elements have no `id` attributes, which means `<label htmlFor>` explicit association is not available. Wrapping labels work in modern browsers but some older AT (JAWS < 19, Narrator on Win10) may not read wrapped labels reliably on `type="email"`. Additionally the required-star visual indicator `<span aria-hidden="true" className="text-primary"> *</span>` at line 172 does not have a programmatic `required` attribute on the input itself — the `required` attribute on the name input is conditional (`required={isGift}`, line 178), which is correct, but there is no `aria-required="true"` to reinforce for AT when the field is conditionally required before form open.
**Fix:** Add `id` + `htmlFor` pairs to each label/input pair. Add `aria-required="true"` when `isGift` is true.
**WCAG:** 1.3.1 Info and Relationships

### N-08 — EmbeddedMollieCheckout: `<label htmlFor>` points to a `<div>`, not an `<input>` (WCAG 1.3.1 FAIL) — HIGH
**File:** `components/adopt/embedded-mollie-checkout.tsx:377-399`
**Code:**
```tsx
<label htmlFor="mollie-card-number" ...>Card number</label>
<div id="mollie-card-number" ... />
```
All four card field labels use `htmlFor` targeting a `<div>`. The Mollie SDK injects its iframe/input inside the `<div>`, but the `<label>` is programmatically associated with the `<div>` container, not the actual injected `<input>`. Click on the label focuses the `<div>`, not the iframe input. Screen readers will announce "Card number, group" (ARIA implicit role of div), not "Card number, edit text" as expected. This is a WCAG 1.3.1 failure.
**Fix:** This is a Mollie Components architecture constraint — the SDK mounts a shadow DOM / iframe into named divs. The accessible pattern for third-party embedded payment fields is to use `<label aria-hidden="true">` to suppress the broken association, and supply a visible heading + `aria-label` on the container div. Alternatively, wrap in `<fieldset>` + `<legend>Card payment details</legend>` and change individual div labels to `aria-label` on the container divs. The exact fix depends on what the Mollie SDK exposes to AT (needs device testing).
**WCAG:** 1.3.1 Info and Relationships

### N-11 — my-adoption/page.tsx: `<section>` elements inside `<main>` have no `aria-label` (WCAG 1.3.1 / 2.4.6) — MEDIUM
**File:** `app/[locale]/my-adoption/page.tsx:168, 231, 302, 348, 395, 428`
The donor portal uses multiple `<section>` elements. In HTML5 / ARIA, `<section>` creates an implicit ARIA `region` landmark only when it has an accessible name (`aria-label` or `aria-labelledby`). Without a name, AT agents that list landmarks skip unlabelled sections. The `PaymentHistoryTable` has `aria-labelledby="donor-payment-history-heading"` (line 89 of payment-history-table.tsx) — that is correct. The inline `<section>` blocks in page.tsx (alpaca card, subscription summary, payment mandate, action buttons, referral) all lack `aria-label` or `aria-labelledby`.
**Fix:** Add `aria-label="Subscription summary"` etc. to each section, or add `id` to the `<h2>` inside each section and use `aria-labelledby`.
**WCAG:** 1.3.1 Info and Relationships, 2.4.6 Headings and Labels

### N-13 — CampaignBannerGeneric: `role="status"` + `aria-live="polite"` on a non-live-updating element (WCAG 4.1.2) — LOW
**File:** `components/campaign-banner-generic.tsx:48-50`
```tsx
<div role="status" aria-live="polite" ...>
```
`role="status"` + `aria-live` is semantically meant for regions that update dynamically at runtime (e.g. a "Saved!" confirmation). The campaign banner is static server-rendered content that appears on page load, never updates in the DOM. AT will not announce it on load if it was already present in the initial HTML. Using `role="status"` here is incorrect — it misleads AT about the nature of the content and wastes the live-region budget. The banner is promotional content; it should be `role="complementary"` or simply a `<div>`.
**Fix:** Remove `role="status"` and `aria-live="polite"`. The element can keep its decorative class.
**WCAG:** 4.1.2 Name, Role, Value

### N-14 — cookie-consent-v3.tsx: banner a11y delegated to vanilla-cookieconsent library (HEURISTIC) — MEDIUM
**File:** `components/cookie-consent-v3.tsx`

- Heuristic: library is reputable and designed for a11y. Mark as LOW-MEDIUM concern pending live device test.
**Action:** Verify with screen reader in production. Ensure the library's consent modal traps focus and restores to the trigger on close.

### N-15 — BundleCta: external link missing accessible affordance (WCAG 2.4.4) — LOW
**File:** `components/tours/bundle-cta.tsx:63-70`
```tsx
<Link href={url} target="_blank" rel="noopener noreferrer" ...>
  Book bundle →
</Link>
```
The "Book bundle" link opens in a new tab (`target="_blank"`) but has no visible or accessible indicator that it leaves the current context. WCAG 2.4.4 (Link Purpose) expects links that open a new window to communicate this to users who cannot observe the browser-level tab change.
**Fix:** Add `aria-label="Book bundle (opens in new tab)"` or append a visually-hidden span `<span className="sr-only"> (opens in a new tab)</span>`.
**WCAG:** 2.4.4 Link Purpose
