# Accessibility Audit — Alpacas Ibiza Redesign
**Report ID:** a11y-001  
**Date:** 2026-05-27  
**Scope:** Heuristic WCAG 2.1 AA against source code. No live a11y tooling or screen reader.  
**Files inspected:** app/[locale]/layout.tsx, app/layout.tsx, components/header.tsx, components/footer.tsx, components/hero.tsx, components/contact-form.tsx, components/commission-form.tsx, components/newsletter-form.tsx, components/faq.tsx, components/sticky-booking-bar.tsx, components/alpaca-card.tsx, components/language-switcher.tsx, app/[locale]/tours/page.tsx, app/[locale]/adopt/page.tsx, app/globals.css

---

## Rule-by-Rule Findings

### 1. Skip-to-Content (WCAG 2.4.1)
**PASS**  
`app/[locale]/layout.tsx:64-69` — skip link is present, visually hidden until focused (`sr-only focus:not-sr-only`), targets `#main-content`, has correct `z-index` (1001), styled with foreground/background on focus. Implementation is correct.

---

### 2. `<main>` Landmark (WCAG 1.3.6 / 2.4.3)
**PASS (with a note)**  
`app/[locale]/layout.tsx:71` — `<main id="main-content">` wraps `{children}` in the locale layout.  
`app/[locale]/adopt/page.tsx:108` — `adopt` page adds a *second* `<main>` inside the locale layout's `<main>`, producing nested `<main>` elements. This is invalid HTML and confuses AT. All other sampled pages (tours) return fragments (`<>…</>`), so this is isolated to `adopt`.

**FAIL on adopt/page.tsx** — the page renders `<main>` but is already inside the locale layout's `<main>`. Remove the inner `<main>` from adopt, replace with `<article>` or `<div>`.

---

### 3. `<nav>` Landmark / `aria-label` (WCAG 1.3.1 / 4.1.2)
**FAIL**  
`components/header.tsx:29` — the `<nav>` element has no `aria-label`. The footer uses no `<nav>` at all (just `<ul>` lists). When two or more landmark regions of the same type exist, WCAG requires each to be distinguishable via `aria-label`. There are two navigation regions (header nav and footer lists). Header `<nav>` should have `aria-label="Main navigation"` and footer link groups should either be wrapped in `<nav aria-label="Footer">` or left as `<ul>` without `<nav>` (current pattern is acceptable but the header `<nav>` must be labeled).

---

### 4. Mobile Menu — Focus Trapping (WCAG 2.1.2)
**PASS**  
`components/header.tsx:57-89` — the mobile menu uses shadcn `<Sheet>` / `<SheetContent>`, which is built on Radix UI Dialog. Radix traps focus inside the panel when open, handles Escape to close, and restores focus to the trigger on close. No custom focus management needed. This is correctly delegated to the library.

---

### 5. Form Labels — Every Input Explicitly Labeled (WCAG 1.3.1 / 3.3.2)
**FAIL (commission-form.tsx, newsletter-form.tsx)**

**contact-form.tsx** — PASS. All inputs use `htmlFor` + matching `id` (`contact-name`, `contact-email`, `contact-subject`, `contact-message`). Full `aria-invalid`, `aria-required`, `aria-describedby` on error. Excellent.

**commission-form.tsx** — FAIL. `components/commission-form.tsx:59,70,81` — every `<label>` is present but has no `htmlFor`, and every `<input>` / `<textarea>` has no `id`. The label text is visually adjacent but programmatically disassociated. A screen reader user tabbing to the name input will hear "name, edit text" with no label read.

**newsletter-form.tsx** — FAIL. `components/newsletter-form.tsx:48-55` — the email `<input>` has no `<label>` at all. It relies solely on `placeholder` text. WCAG 1.3.1 explicitly states placeholder alone does not satisfy label requirement (disappears on input, insufficient colour contrast, no persistent label).

---

### 6. Button vs Link Semantics (WCAG 4.1.2)
**PASS (mostly)**  
- `<Button asChild>` + `<a href>` pattern is used correctly throughout (header book CTA, hero CTAs, adopt CTAs). `asChild` renders `<a>` not `<button>`, which is correct for navigation.  
- `sticky-booking-bar.tsx:35-42` — MINOR ISSUE: an `<a>` wraps a `<Button>`. This renders as `<a><button>` which is invalid HTML (interactive element inside interactive element). Browsers will behave inconsistently. Fix: use `<Button asChild><a href=…>` or drop the inner Button and style the `<a>` directly.  
- FAQ buttons are `<button>` elements. Correct.

---

### 7. Heading Order — No Skips (WCAG 1.3.1 / 2.4.6)
**PASS (tours, adopt) / WARN (hero)**  
- `app/[locale]/tours/page.tsx` — h1 (Hero via `hero.tsx:63`), h2 (tour options, plan visit, booking, reviews). Order is sequential.  
- `app/[locale]/adopt/page.tsx` — h1 (adopt hero), h2 (tier label, benefits, CTA). Sequential.  
- `hero.tsx:63` — the `<Hero>` component always renders an `<h1>`. If a page embeds Hero but already has an h1 outside Hero (or two routes use Hero in a sub-section), this would duplicate h1. Based on sampled pages this does not happen, but it is a fragile implicit contract.

---

### 8. Image Alt Text (WCAG 1.1.1)
**PASS (with a warning)**  
- `components/alpaca-card.tsx:23-26` — `<Image alt={alpaca.name}>` provides the animal's name. Acceptable for identification. If the name is not descriptive (e.g. just "Pepe"), it does not tell AT what the image depicts visually. Minimum pass; better would be `alt="${alpaca.name} — an alpaca at Es Currals"`.  
- `components/hero.tsx:37-45` — background video has no `<track>` for captions and no `aria-label` on the `<video>` element. Decorative use (background atmosphere) with no controls is arguable; however WCAG 1.2.1 requires audio-only or video-only content that is prerecorded to have a text alternative. If the video has no meaningful audio, `aria-hidden="true"` on the `<video>` is the correct pattern. Currently neither is applied.  
- Background images via CSS `style={{ backgroundImage: … }}` in `hero.tsx:52-57` are decorative by nature (no AT reads CSS backgrounds). PASS.  
- Tour card icons in `tours/page.tsx:162` — emoji rendered as text nodes (`🦙`, `🧵`, etc.). No `aria-hidden="true"`. These will be read aloud by screen readers ("llama emoji", "thread emoji"). Add `aria-hidden="true"` to the wrapper `<div>`.  
- Footer WhatsApp emoji at `footer.tsx:94` — `aria-hidden="true"` already applied. PASS.

### 9. Color Contrast — Light Mode (WCAG 1.4.3)
Calculated from `app/globals.css` HSL values converted to relative luminance.

| Color pair | Ratio | AA Normal (4.5) | AA Large (3.0) |
|---|---|---|---|
| Foreground (#43 4C 56) on Background (#FA FA FA) | **8.36:1** | PASS | PASS |
| Primary olive (#54 6A 2F) on Background | **5.78:1** | PASS | PASS |
| White on Primary (#54 6A 2F) — button text | **5.78:1** | PASS | PASS |
| Muted-foreground (#60 6E 7A) on Background | **5.63:1** | PASS | PASS |
| **Foreground/70 (muted body text, opacity blend)** | **3.82:1** | **FAIL** | PASS |
| **White on Accent (#DD 7F 3C) — CTA buttons** | **2.93:1** | **FAIL** | **FAIL** |

**Two failures:**  
1. `text-foreground/70` class used heavily for body copy (hero subtitle, card descriptions, footer text, form hints). At 3.82:1 it passes large-text (18px+ or 14px bold) but fails for normal body text at 16px/400 weight. Widespread across all pages.  
2. **White text on accent (`#DD7F3C`)** at 2.93:1 fails both thresholds. This affects: hero primary CTA button, header "Book Tour" button, commission form submit button, sticky booking bar button. These are the highest-traffic CTAs on the site.

### 10. Focus Visibility (WCAG 2.4.7)
**PASS (components) / WARN (raw `<a>` elements)**  
- Custom form inputs in contact-form.tsx use `focus:ring-2 focus:ring-primary`. PASS.  
- shadcn `<Button>` components include `focus-visible:ring-2` via their base styles. PASS.  
- Raw `<a>` elements used as CTAs in `adopt/page.tsx:195-207` (`inline-block rounded-lg…`) have no `focus-visible` class. They will get the browser default outline, which on Chrome/Edge is adequate but not styled to match the design system. Minor cosmetic issue; functionally navigable.  
- `tours/page.tsx:288-291` — inline `<a>` for FareHarbor fallback link has no `focus-visible` styling.

---

### 11. Animation / prefers-reduced-motion (WCAG 2.3.3 — AAA / 2.1 best practice)
**FAIL**  
No `prefers-reduced-motion` handling anywhere in the codebase (confirmed via grep across all `.tsx` files). The following animate unconditionally:  
- `hero.tsx:36-45` — autoplaying background video (continuous motion).  
- `components/analytics-dashboard.tsx:42` — `animate-spin` loading spinner.  
- `components/product-card.tsx:54` — `group-hover:scale-105 transition-transform` image zoom.  
- `components/sticky-booking-bar.tsx:32` — `transition-transform` slide-in/out.  
- All shadcn UI animations (accordion open/close, sheet slide, dialog fade). Radix UI does respect `prefers-reduced-motion` in its CSS keyframes — the Tailwind `animate-*` utilities however do not.  
The video is the most impactful issue for vestibular disorders.

---

### 12. Locale Switcher — `lang` Attribute on Options (WCAG 3.1.2)
**FAIL (root layout) / PASS (switcher options — limited)**  
`app/layout.tsx:44` — `<html lang="en">` is hardcoded to `"en"` regardless of the active locale. The locale layout `app/[locale]/layout.tsx` wraps content in a `<div>`, not an `<html>`, so it cannot override the `lang` attribute. This means a French (`/fr/`) or Spanish (`/es/`) user receives a page declared as English. Screen readers will mispronounce translated content.  
`components/language-switcher.tsx` — individual `<SelectItem>` elements do not have `lang` attributes on them; they display flag emoji + locale name which is sufficient for visual identification but not programmatic. Minor.

**Additionally:** `viewport` in `app/layout.tsx:34` sets `userScalable: false` (renders as `user-scalable=no`). This violates WCAG 1.4.4 (Resize Text) and is a hard failure — it prevents users who rely on pinch-to-zoom from enlarging text.

## The Single Most Painful Gap

**`html lang="en"` hardcoded while the site serves 4+ locales.** Every non-English page (French, Spanish, Dutch) will be announced in English pronunciation by screen readers. For a multilingual tourism site in Ibiza attracting Spanish, Dutch, German, and French speakers, this is the gap with the broadest real-world harm — it affects every non-English AT user on every non-English page.

## CAN'T DO WITHOUT HELP

- **Actual screen-reader testing** (NVDA + Firefox, VoiceOver + Safari) — required to verify announcement order, label reads, and focus restoration.  
- **Real color rendering on the deployed site** — the contrast calculations above are based on raw HSL values. Real browsers apply subpixel rendering, dark-mode overrides, and the FareHarbor iframe injects its own stylesheet which may introduce additional contrast failures.  
- **Keyboard-only navigation walkthrough** — especially through the FareHarbor calendar embed (third-party; we cannot audit the iframe).  
- **4G / low-vision zoom testing** — the `user-scalable=no` failure was found in code; actual behavior across browsers (some ignore it) needs verification by a real user who relies on zoom.  
- **Color blindness simulation** — the olive primary and warm accent may be indistinguishable under deuteranopia; Figma / Stark plugin needed on rendered screenshots.
