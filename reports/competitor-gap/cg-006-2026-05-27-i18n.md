**Source:** `python3` comparison of all 6 `translations/*.json` files.

The 284 missing keys cover: `adopt.*`, `experiences.romanticSunset.*`, `gifts.*`, `nav.journal`, admin strings, and several CTA/error strings added after the initial translation pass. The silent English fallback in `lib/translations.ts` means these silently render English on DE/IT/ES/FR pages.

## 3. Hreflang Detail

`app/[locale]/layout.tsx:30-32` generates `alternates.languages` for the root layout — this is correct and covers all top-level locale roots (`/en`, `/de`, …).

**Gaps:**
1. **No `x-default`** in any `alternates.languages` object. Google uses `x-default` to identify the canonical fallback when no locale matches. Without it, Google may pick an arbitrary locale as default.
2. **Sub-pages only declare `canonical`, not sibling locales.** `/adopt`, `/tours`, `/shop/*`, `/experiences/*`, `/journal`, etc. generate `alternates: { canonical: '/${locale}/adopt' }` only — no `languages` map. Google cannot discover locale variants of these pages from their own `<head>`.
3. **No sitemap.xml** (`app/sitemap.ts` does not exist). Hreflang can also be declared in sitemaps; without either head tags or a sitemap for sub-pages, Google is missing the cross-locale graph for 15+ pages.

## 4. Five Specific i18n Improvements for Alpaca

### GAP-1 (Correctness risk — highest): Add `x-default` to all `alternates.languages` maps
**File:** `app/[locale]/layout.tsx:30-32`  
All `alternates.languages` blocks must include `'x-default': '/en'` (or redirect-to-best-fit URL). Without it Google cannot determine which locale to show users whose browser language doesn't match any served locale. This is a SEO correctness issue — Google's indexing of locale variants degrades without `x-default`.

```ts
// Current (broken for x-default):
languages: Object.fromEntries(i18nConfig.locales.map((l) => [l, `/${l}`]))

// Fixed:
languages: {
  ...Object.fromEntries(i18nConfig.locales.map((l) => [l, `/${l}`])),
  'x-default': '/en',
}
```

### GAP-2 (SEO): Propagate `alternates.languages` to all deep sub-pages
**Affected files:** `app/[locale]/adopt/page.tsx`, `app/[locale]/tours/page.tsx`, all `app/[locale]/shop/*/page.tsx`, `app/[locale]/experiences/*/page.tsx` (15+ pages).  
Each page's `generateMetadata` currently sets only `canonical`. They need the full locale map:
```ts
languages: Object.fromEntries(
  i18nConfig.locales.map((l) => [l, `/${l}/${slug}`])
  .concat([['x-default', `/en/${slug}`]])
)
```
A shared helper in `lib/i18n-metadata.ts` would DRY this across all pages.

### GAP-3 (Translation quality): Add dev-mode missing-key warnings
**File:** `lib/translations.ts:25-28`  
The silent English fallback is correct for production but hides translation gaps during development. Add a `process.env.NODE_ENV === 'development'` guard that logs `[i18n] missing key "${key}" for locale "${locale}"` to the console when falling back. This is the same pattern next-intl uses by default and lets the developer surface the 284 missing DE/IT/ES/FR keys without a separate audit script.

### GAP-4 (Data correctness): Centralise locale-aware number/date formatting
**Affected files:** `components/product-card.tsx:52`, `components/analytics-dashboard.tsx:87-89`, `components/legal-version-stamp.tsx:13`, `app/api/reminder/route.ts:44`, `app/api/fareharbor-webhook/route.ts:136`  
`toLocaleString()` without a locale argument uses the server's OS locale (likely `en-US` on Node/Vercel), not the visitor's locale. Create `lib/format.ts` with `formatCurrency(locale, amount)` and `formatDate(locale, date, opts)` wrappers that always pass `locale` explicitly. Replace the 5+ scattered call sites.

### GAP-5 (Completeness): Close the 284-key translation gap before launch
**Files:** `translations/de.json`, `translations/it.json`, `translations/es.json`, `translations/fr.json`  
The 40% missing rate means every German/Italian/Spanish/French visitor hitting `/adopt`, `/gifts`, the romantic-sunset experience, or any journal page gets English text with no warning. At minimum, document the untranslated keys in `OWNER_INPUT_NEEDED.md` as a launch blocker and add a CI check (e.g. `scripts/check-i18n.ts`) that diffs non-EN files against EN and exits non-zero if coverage drops below 95%.

## 5. One Thing Alpaca Does Better Than the References

**Locale detection order is more complete than the Vercel/Next.js baseline.**  
The official Next.js docs demonstrate only Accept-Language → redirect. Alpaca's `middleware.ts` correctly implements all three signals — path prefix, then `NEXT_LOCALE` cookie, then `Accept-Language` header — matching next-intl's production-recommended precedence order, and does so without a third-party library. This is genuinely correct, production-grade middleware that most of the reference examples do not show fully.
