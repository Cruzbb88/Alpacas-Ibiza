# Localization Quality Audit — loc-quality-001
**Date:** 2026-06-13
**Auditor:** Claude (automated measurement — all counts verified from live JSON files)
**Files audited:** `translations/{en,nl,de,es,fr,it}.json`, `next-intl.config.ts`, `i18n.config.ts`, `app/[locale]/layout.tsx`, `components/mobile-sticky-booking-bar.tsx`, `lib/i18n-plurals.vitest.ts`

---

## Executive Verdict

**2 locales are genuinely shippable today: `en` and `nl`.**

The other 4 (de, es, fr, it) are scaffolded at 57–59% coverage. The fallback system (`next-intl.config.ts` `mergeWithEnBase`) is correctly implemented, so a German visitor NEVER sees raw keys or `__UNTRANSLATED__` strings — they see graceful English fallback everywhere a German translation is absent or sentinel. The UX is NOT broken; it is degraded. The visitor experiences a mixed-language page: German on the sections that were translated (About, tours headline, home hero), English everywhere else (adopt page = 92% English, nav = 83% English, gifts page = 100% English, alpacas section = 97% English).

The honest competitive position: **the site has 2 shippable locales plus 4 scaffolded shells.** Whether to call this "6 locales" in marketing is a business decision with real SEO risk (see Section 5).

## 1. Real-vs-Sentinel Table (Precise Key Counts)

**Methodology:** Flattened all nested JSON to dot-notation keys. A key is "sentinel" if its value contains `__UNTRANSLATED__`, `UNMAPPED`, `OWNER_REVIEW`, or `__OWNER_INPUT_REQUIRED__`. A key is "identical-to-en" if the locale value exactly matches the en value and is not a sentinel. "Genuinely localized" = all keys minus sentinel minus identical-to-en. For de/es/fr/it, the ~680 keys absent from the locale file are NOT counted in that locale's total — they simply don't exist in those files and fall back via `mergeWithEnBase`.

| Locale | Total keys (in file) | Genuinely localized | Sentinel | Identical to en (passthrough) | Missing from file (en has, locale lacks) | % Genuinely localized (of en total 1348) |
|--------|---------------------|--------------------|---------|-----------------------------|------------------------------------------|------------------------------------------|
| **en** | 1348 | 1334 | 14 | — | — | 99.0% |
| **nl** | 1333 | 1274 | 12 | 47 | 25 (absent) | 94.5% |
| **de** | 684 | 393 | 277 | 14 | 664 (absent from en) | 29.2% |
| **es** | 684 | 404 | 277 | 3 | 664 (absent from en) | 30.0% |
| **fr** | 684 | 393 | 277 | 14 | 664 (absent from en) | 29.2% |
| **it** | 684 | 398 | 277 | 9 | 664 (absent from en) | 29.5% |

**Critical structural finding:** de/es/fr/it each contain **684 total keys** (the original translation batch), while en now has **1348** — meaning **664 keys were added to en after the original locale files were created**, and those keys are entirely ABSENT from the 4 weak locales. On top of that, 277 of the 684 present keys are `__UNTRANSLATED__` sentinels from a May 2026 gap-injection pass (see `reports/i18n/i18n-gap-2026-05-27.md`). The net result: de/es/fr/it have genuine translations for only **393–404 keys** out of 1348 en keys (~29–30%).

### What "absent" vs "sentinel" means for rendering

- **Absent keys** (664 of them): The key does not exist in the locale file. `mergeWithEnBase` in `next-intl.config.ts` fills these from the en base at request time. Visitor sees English — graceful, not broken.
- **Sentinel keys** (277 of them): The key exists in the file with value `__UNTRANSLATED__: <en text>`. The `isAbsent()` guard in `next-intl.config.ts:13-19` detects `startsWith('__UNTRANSLATED__')` and treats them as absent. `mergeWithEnBase` then substitutes the en base value. Visitor sees English — graceful, not broken.

**Both categories produce identical runtime behavior: English text renders.** No raw keys, no sentinel strings leak to visitors. The fallback system works correctly.

## 2. Fallback Behavior — What a German Visitor SEES

### Mechanism (next-intl.config.ts:33-73)

`mergeWithEnBase(en, de)` deep-merges the locale file ON TOP of the English base. Every key the locale translates wins; every key it lacks or sentinels falls through to English. `stripSentinels()` runs afterward to remove any `__UNTRANSLATED__` values that survived. The `getMessageFallback` hook (line 150-158) only fires for keys absent from BOTH the locale AND en — which cannot happen in practice since en is the base.

### Three Concrete Traced Examples (German, /de pages)

**Example 1 — `nav.visit` (Navigation item "Visit")**
- en value: `"Visit"`
- de value in file: `"__UNTRANSLATED__"` (sentinel, line present in de.json)
- Mechanism: `isAbsent("__UNTRANSLATED__")` returns `true` → `mergeWithEnBase` substitutes en base
- What renders on /de: **"Visit"** (English — graceful fallback)
- Status: Broken from a localization standpoint, but UX is not visibly broken

**Example 2 — `nav.home` (Navigation item "Home")**
- en value: `"Home"`
- de value: ABSENT from de.json (one of 664 missing keys)
- Mechanism: Key does not exist in de, `mergeWithEnBase` iterates en keys and finds no override → en base value used
- What renders on /de: **"Home"** (English — graceful fallback)
- Note: "Home" is the same word in German, so this particular passthrough is semantically invisible. But this is coincidence, not design.

**Example 3 — `adopt.title` (Adopt page H1: "Adopt an Alpaca")**
- en value: `"Adopt an Alpaca"`
- de value: ABSENT from de.json (one of 151 absent adopt.* keys)
- Mechanism: Key absent → en base used
- What renders on /de/adopt: **"Adopt an Alpaca"** (English — graceful fallback)
- Impact: The entire adopt page (92% English fallback) presents a German URL (`/de/adopt`) with almost entirely English content

### `MobileStickyBookingBar` raw-key guard (components/mobile-sticky-booking-bar.tsx:172-176)

```typescript
const rawAdoptCta = tr('nav.adoptCta')
const rawBookTour = tr('nav.bookTour')
const adoptCtaLabel = rawAdoptCta && rawAdoptCta !== 'nav.adoptCta' ? rawAdoptCta : 'Adopt an alpaca'
const bookTourLabel = rawBookTour && rawBookTour !== 'nav.bookTour' ? rawBookTour : 'Book a tour'
```

The guard checks whether `tr()` returned the raw key itself (`'nav.adoptCta'` or `'nav.bookTour'`). This guard is **redundant but harmless** given the `mergeWithEnBase` fallback — `tr()` should never return the raw key for any key that exists in en. However, it is correct defensive coding: if `nav.adoptCta` is sentinel in de, `mergeWithEnBase` substitutes the en value `"Adopt an Alpaca"`, which is neither empty nor the raw key, so the guard passes the en value through cleanly. **No sentinel leaks to the UI from this component.**

### Currency formatting — hardcoded vs locale-aware

Currency values are **hardcoded strings in the translation files**, not Intl.NumberFormat calls. Examples:

- `adopt.monthlyPrice`: `"€75 / month"` in en — this key is **absent in all 4 weak locales** and falls back to the English string
- `tours.planVisit.pricing.starting`: correctly localized per locale:
  - de: `"Ab 30 € pro Person"` — uses German word order (amount first, currency after)
  - es: `"Desde 30 € por persona"`
  - fr: `"À partir de 30 € par personne"`
  - it: `"Da 30 € a persona"`

**Finding:** The tour pricing string is correctly locale-adapted (German `30 €` vs English `€30` word order). However, the adopt page prices (`€75/month`, `€900/year`) are hardcoded English strings that fall back from absent locale keys. These are present on the highest-revenue page but are still readable to non-English speakers (€ symbol is universal). Not technically broken; not localized.

**No Intl.NumberFormat or Intl.DateTimeFormat calls were found in the translation pipeline.** Currency amounts are embedded as string literals. The risk is low for this product (EUR pricing, European market) but the architecture does not support locale-specific number formats (e.g., German `1.234,56 €` vs English `€1,234.56`). For the current price range (€75, €900) this is a non-issue since no decimal formatting is needed.

## 5. The Honest Competitive Claim

### What "6 locales" means today

| Locale | Status | Evidence |
|--------|--------|---------|
| en | Shippable — 99% coverage | 1334/1348 keys translated |
| nl | Shippable — 95% coverage, all key pages 91–100% | 1274/1333 keys, 0 absent gifts/adopt/tours |
| de | Scaffolded — 29% of en keys genuinely translated | 393/1348 genuine, 277 sentinel + 664 absent |
| es | Scaffolded — 30% genuine | 404/1348 |
| fr | Scaffolded — 29% genuine | 393/1348 |
| it | Scaffolded — 30% genuine | 398/1348 |

### SEO thin-content risk

Google's hreflang implementation (`lib/i18n-metadata.ts:buildLocaleAlternates`) emits alternate links for all 6 locales on every page. If de/es/fr/it are indexed, Google will crawl `/de/adopt`, `/de/gifts`, `/de/alpacas` and find pages with:
- A German URL slug
- English content (92–100%)
- A `lang="de"` attribute on the html element

This is the definition of thin content / language mismatch. Google may:
1. Ignore the hreflang and serve the de URL to German searchers anyway (content mismatch)
2. Deindex or penalize the de/es/fr/it URLs for duplicate-content-with-wrong-language
3. Cannibalize the en ranking if de/fr/es/it URLs are seen as thin copies

The current `robots.ts` (`lib/robots-env.ts:isProductionEnv()`) disallows all crawling on non-production environments. **If the site is deployed to production with 6 locale routes active, Googlebot will index all 6 — including the 4 scaffold locales.** This is a real SEO risk, not a theoretical one.

### Three options — evidence, tradeoffs, no recommendation on which to pick (Cruz decides)

**Option A: Ship 2 locales now, hide de/es/fr/it**

Mechanism: Restrict `i18nConfig.locales` to `['en', 'nl']` OR redirect de/es/fr/it to en at the middleware layer OR `noindex` the 4 weak locales in their metadata.

- Pros: No thin-content risk. Honest "2 locales" claim. Simpler URL structure. German/French/Spanish/Italian visitors get clean English rather than a confusing mixed-language experience.
- Cons: Loses the 4 locale URL slots. If translations are completed later, re-indexing takes weeks. Hreflang equity built on existing URLs is lost.
- SEO: Clean. No penalty risk.

**Option B: Ship 6 locales with en-fallback as-is (current state)**

Mechanism: Keep current behavior. The fallback system is working; the UX is graceful English, not broken.

- Pros: All 6 locale URLs are live and crawlable. A native German speaker landing on /de/tours (72% German) gets a good experience. `/de/about` (94%) is excellent. The scaffolding is already in place; completing translations adds value incrementally.
- Cons: `/de/adopt` (8% German), `/de/gifts` (0%), `/de/alpacas` (3%) are effectively English pages with German URLs — thin-content risk is real. A German visitor who clicks through from a German Google result to /de/adopt will see English, which is a trust/conversion penalty.
- SEO: Moderate-to-high risk for adopt/gifts/alpacas pages. Tours and About pages are defensible.

**Option C: Ship 6 locales but noindex the weak pages per-locale**

Mechanism: For de/es/fr/it, add `robots: { index: false }` to the metadata of pages with <50% coverage (adopt, gifts, alpacas). Keep tours and about indexable.

- Pros: Protects SEO on the worst pages. Allows German users to reach /de/tours (72%) organically. Does not require removing locale routes.
- Cons: Implementation work required. Requires per-page locale-coverage logic at build time. The hreflang alternates still point to noindexed pages, which Google ignores — dilutes hreflang signal.
- SEO: Better than Option B for the risky pages; more complex than Option A.

### CODE-DOABLE vs OWNER-DATA split

| Category | What it needs | Owner or dev? |
|----------|--------------|---------------|
| Fix noindex on weak pages (Option C) | Add locale + coverage check to generateMetadata per page | Dev (code-doable) |
| Restrict to 2 locales (Option A) | Edit i18nConfig.locales or add middleware redirect | Dev (code-doable) |
| Complete de/es/fr/it translations | 955 untranslated/absent keys × 4 locales = 3,820 translation units | OWNER-DATA — requires human translators |
| ICU plural translation for socialProof keys | 3 keys × 4 locales = 12 strings | OWNER-DATA (small — a translator could do this in 30 min) |
| Currency format consistency for adopt page | 8 adopt price keys × 4 locales = 32 strings | OWNER-DATA — trivial once translations start |
| SEO decision (ship 2 vs 6 vs hybrid) | Policy decision on marketing claim | OWNER decision |

The fallback infrastructure is correct and production-safe. The gap is entirely translation content, not code. No code changes are required for the fallback to work safely. The only code change needed is if Cruz/owner chooses Option A (hide weak locales) or Option C (selective noindex).
