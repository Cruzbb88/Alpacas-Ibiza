# Resonance Finder — rf-002 — Tunable Knob Inventory (lib/ + dependent routes)

Follow-up to rf-001 (broad sweep). This pass narrows on the **single shared timeout primitive** (`fetchWithTimeout`) and the cluster of timeouts, batch sizes, ISR TTLs, and scheduling lead-times that depend on it. The unifying question: are the values that travel through `lib/fetch.ts` and `lib/turnstile.ts` internally consistent, and where are knobs left implicit?

## L3 — Optimal Value Determination (Top 5)

### 1. A1 · `fetchWithTimeout` default `ms` — **5000 → 6000 ms**
- **Why:** Default is silently inherited by A3 + A4 (FareHarbor items + availability fetches). FareHarbor's external API p95 latency is anecdotally 2–4 s; under European peak load 5 s aborts cleanly-succeeding requests. Bumping to 6000 ms matches the explicit Google Places choice (A5) and keeps total page wait under 7 s including TLS handshake.
- **Tradeoff:** 1 extra second of user-visible hang on a truly-dead upstream.
- **Validation test:** Synthetic test that mocks `fetch` with a 5500 ms delay; assert `fetchWithTimeout` resolves at 6000 ms default, aborts at 5500 ms when called with `ms=5500`. Add to `lib/fetch.test.ts`.

### 2. A2 · Turnstile verify timeout — **5000 → 3500 ms**
- **Why:** Cloudflare publishes a <500 ms p99 SLA for `siteverify`. 3.5 s covers two retransmits even on a flaky link. Lowering means a fail-closed prod state arrives sooner, surfacing a real Cloudflare outage to the user instead of hanging the submit button for 5 s.
- **Pre-req:** Should land **with** E1 (single retry) so the budget becomes 3.5 s × 2 attempts = ~7 s worst-case rather than 5 s × 1.
- **Validation test:** End-to-end: block `challenges.cloudflare.com` in `/etc/hosts` during a staging form submit; verify the form returns a fail-closed error within 4 s, not 5+.

### 3. B2 · Availability ISR — **keep 1800 s** (validated)
- **Why:** ADR-008 already justifies this with a 4-row matrix. Rate-limit pressure on FareHarbor escalates non-linearly under traffic spikes; lowering below 1800 s erodes the entire purpose of the ISR. Higher (3600 s) increases sold-out-shown-as-available risk during peak booking windows.
- **Recommendation:** No change. Promote constant to a named export (`AVAILABILITY_REVALIDATE_S`) so the link to ADR-008 is grep-able.

### 4. D1 · `REMINDER_LEAD_MS` — **expose as env var, keep 48 h default**
- **Why:** 48 h is a defensible default but `process.env.REMINDER_LEAD_HOURS` gives the operator a no-deploy tuning knob. Wedding bookings (commission tours) may benefit from 72 h; spontaneous yoga bookings benefit from 24 h.
- **Validation test:** `webhook-router.test.ts` already tests `computeScheduleWindows` — add a test that the constant honors an env override.

### 5. E1 · Retry in `fetchWithTimeout` — **add 1 retry on network error / 5xx**
- **Why:** A single transient FareHarbor failure currently kills the availability grid for the full ISR window. One retry with 250 ms backoff lifts success rate from ~99 % to ~99.99 % on independent failure assumption. Already proposed in `reports/exploding-pen/ep-001` G-07; resonance analysis confirms this is the highest-leverage missing knob.
- **Constraint:** Skip retry on 4xx (Turnstile token reuse is non-idempotent — must not double-submit to Cloudflare).
- **Validation test:** Mock `fetch` to fail once with 500, succeed second call; assert single retry, total elapsed < `(ms + 250)`.

## L4 — Harmonic Analysis

### Resonance points (parameter interactions)

**R1 · Turnstile timeout ↔ Availability fan-out timeout — BUDGET MISMATCH**
- Turnstile (A2) blocks the form submit on 5 s.
- Availability (A3 + A4) fan-out runs at 5 s **per item**, with `.slice(0, 3)` items in parallel via `Promise.allSettled`. Worst-case 5 s wall-clock (not 15 s — they're parallel), but the **route handler has no overall ceiling**. If A1 default rises to 8 s and a 4th item slips past C1, the user-visible booking-section render budget would silently expand. The default in `lib/fetch.ts` is the **single point that controls both the bot-protection and the booking-grid latency budget**. They should not share a default.
- **Recommendation:** Stop relying on the implicit `A1=5000`. Pass an explicit `ms` to every call site. The default is fine for *unknown* callers but a quiet bug for production paths.

**R2 · Client TTL (B1=60 s) ↔ Server ISR (B2=1800 s) — INTENTIONAL, GOOD**
- Client cache 60 s ≪ server ISR 30 min. The chain is `client → ISR → upstream`. Browser refreshes within 60 s reuse the in-flight promise; within 1800 s hit the ISR; beyond regenerate. This is healthy stacking — each layer is ~30× the inner layer, no resonance.

**R3 · Items cap (C1=3) ↔ Dates cap (C2=8) — IMPLICIT COUPLING**
- The 3-item slice times each item's potential 30-day window. With ~10 availabilities per item per month that's ~30 candidate dates → `Map` dedupe → top 8. If the business adds a 4th tour, C1 silently drops it and the date grid shrinks. Raising C1 to 5 without auditing the fan-out budget could 2× the FareHarbor API load per ISR regen.
- **Recommendation:** Surface C1 as a named constant `MAX_TOUR_ITEMS_FANNED_OUT = 3` with a comment linking to FareHarbor rate-limit headroom.

**R4 · `REMINDER_LEAD_MS` (D1=48 h) ↔ Resend `scheduledAt` max (~30 days)**
- D1 is well within Resend's 30-day max. Tours booked >30 days in advance will have `scheduleReminder = true` but the actual Resend send could fail if the absolute scheduled date exceeds 30 days from `now`. ADR-001 acknowledges this but `webhook-router.ts:computeScheduleWindows` does not check it.
- **Recommendation:** Add a `MAX_SCHEDULED_AHEAD_MS = 29 * 24 * 60 * 60 * 1000` guard in `computeScheduleWindows` and degrade gracefully (skip schedule, log warning) when exceeded.

### Anti-patterns observed

1. **Implicit defaults across module boundaries.** `availability/route.ts` consumes the `lib/fetch.ts` default without passing `ms`. Reader of the route handler cannot see the timeout without crossing files. Three call sites do this; two pass explicit values. The mixed style is the bug.
2. **No retry primitive.** Every external HTTP call has the same shape (`fetchWithTimeout` + try/catch). The retry logic should live with the timeout logic.
3. **Magic numbers without named constants.** `REMINDER_LEAD_MS` is named (good). `1800` for ISR and `5000` for timeouts are not (bad). Names make `git blame` and ADR-cross-references navigable.

## CAN'T DO WITHOUT HELP

1. **Production load patterns** — Vercel Analytics or GA4 sample of `/api/availability` and Turnstile submit volume by hour. Determines whether the 1800 s ISR is over- or under-conservative.
2. **Observed timeout failures** — Vercel runtime logs filtered to `[turnstile] verify failed` and `FareHarbor item availability fetch failed` over 30 days. Real abort frequency would calibrate A1/A2 instead of relying on Cloudflare's stated p99.
3. **User retry behavior** — Submit-button click events from the contact/commission/yoga forms after a fail-closed Turnstile response. Tells us whether E1 (retry) would actually rescue real submissions or whether users have already given up.
4. **FareHarbor rate-limit headers** — Whether their `/availabilities/date-range/` endpoint returns `X-RateLimit-Remaining` or `Retry-After`. Required to bound C1 (items fan-out) safely.
