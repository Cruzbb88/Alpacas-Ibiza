## Top 3 unifications (risk × reward justifies)

### U1 — Extract `isValidEmail()` to `lib/validate-email.ts` (C1)
**Callers affected:** `app/api/reminder/route.ts:39`, `app/api/review-request/route.ts:36`, `lib/webhook-router.ts:114`.
**Proposed abstraction:** New 3-line file `lib/validate-email.ts` exporting `export const EMAIL_REGEX = /^[^\s@]+@[^\s@]+\.[^\s@]{2,}$/; export const isValidEmail = (s: unknown): s is string => typeof s === 'string' && EMAIL_REGEX.test(s)`.
**Migration steps:** (1) create file + test; (2) replace 3 regex literals with `isValidEmail(email)`; (3) optionally add to contact/commission/newsletter routes that currently only check presence (this is a reward expansion, not a refactor — flag separately).
**Rollback:** Revert 3 import lines + delete `lib/validate-email.ts`. No runtime state involved.
**Risk:** 2/10. **Reward:** 6/10 — closes a real drift class (future RFC-5322 tightening or IDN allowance needs one edit, not three).

### U2 — Delete `hooks/use-mobile.tsx` + `hooks/use-toast.ts` duplicates (C4)
**Callers affected:** `components/ui/sidebar.tsx:8` imports `@/hooks/use-mobile`; `components/ui/toaster.tsx:3` imports `@/hooks/use-toast`. No file imports from `@/components/ui/use-mobile` or `@/components/ui/use-toast`.
**Proposed abstraction:** Delete `components/ui/use-mobile.tsx` and `components/ui/use-toast.ts` (the unused twins). Keep the `hooks/` copies because that's where the live imports point. Verified by grep — both `@/components/ui/use-*` paths have zero call sites.
**Migration steps:** (1) `rm components/ui/use-mobile.tsx components/ui/use-toast.ts`; (2) `pnpm build` to confirm zero references; (3) commit.
**Rollback:** `git checkout` the two files.
**Risk:** 2/10 (build verifies dead code). **Reward:** 7/10 — kills a real bug class: future edits to one copy wouldn't reach the other, and `useToast`'s module-scoped `memoryState` would silently split into two stores if anyone ever imported from the wrong path. shadcn scaffold leftover.

### U3 — Wrap webhook-secret guard for the fail-OPEN twin (C2)
**Callers affected:** `app/api/reminder/route.ts:18-24` and `app/api/review-request/route.ts:14-20` — these two blocks are character-identical except whitespace.
**Proposed abstraction:** Add to `lib/secrets.ts`:
```ts
export function requireOptionalWebhookSecret(
  request: Request,
  envKey = 'FAREHARBOR_WEBHOOK_SECRET',
  headerName = 'x-webhook-secret',
): NextResponse | null {
  const expected = process.env[envKey]
  if (!expected) return null            // fail-OPEN: secret unset → allow
  const got = request.headers.get(headerName)
  if (!safeEqual(got, expected)) {
    return NextResponse.json({ error: 'Unauthorized' }, { status: 401 })
  }
  return null
}
```
Routes become: `const authErr = requireOptionalWebhookSecret(request); if (authErr) return authErr`.
**Migration steps:** (1) add helper + unit test in `lib/secrets.test.ts`; (2) swap reminder + review-request; (3) confirm CLAUDE.md failsafe map still accurate (these two routes are NOT in the failsafe table — only fareharbor-webhook is, and we are not touching it).
**Rollback:** Revert imports in 2 route files + revert lib/secrets.ts.
**Risk:** 3/10 — auth code, but the fail-OPEN semantics are explicit and preserved; fareharbor-webhook's fail-CLOSED path is **not** touched, so the failsafe row stays untouched. **Reward:** 7/10 — these two routes drift independently today; one change becomes two.

## Don't-unify list (low reward or high risk)

- **C3 fail-CLOSED webhook auth (fareharbor-webhook:36-48)** — touching this hits the failsafe map at `CLAUDE.md` "Webhook 503 if secret unset". A unified helper that supports both modes is feasible but the cost of breaking the 503-vs-401 distinction outweighs the gain. Only revisit after U3 lands and the helper signature is proven. **Risk 5, Reward 4.**
- **C10 generic singleton store factory** — `bookingScheduleStore` and `rate-limit` both use the `globalThis.__name__` HMR-safe pattern but their value types are different (`Map<string,record>` vs `Map<string,number[]>`), the eviction strategy is different (timestamp-window vs key-set), and the upgrade path is different (Vercel KV record store vs Redis sliding-window). A `createGlobalStore<K,V>()` factory would erase the legible per-file intent without reducing surface area. **Risk 6, Reward 2.**
- **C11 try/catch wrapper around route handlers** — wrapping with `withApiHandler` would hide route-specific status codes (503 vs 401 vs 400 vs 500) and the per-route logging prefix. Current error handling is verbose but each handler is the source of truth for its own failure modes. **Risk 4, Reward 2.**
- **C12 `tr` vs `translate` naming** — zero logic difference; renaming 30+ files is pure churn. **Risk 1, Reward 1.**
- **C7 date-range computation** — three callers, each with slightly different semantics (today→+30d, today→+7d, today-30→today). The shared helper `fmtYmd(d: Date)` could land if a 4th caller appears; not worth a refactor PR today. **Risk 2, Reward 3.**

## STOP

The following need owner / Tony intent before consolidating:

1. **`lib/newsletter.ts:30` SendGrid `fetch()` without `fetchWithTimeout` (C15)** — fix is mechanical (Risk 2, Reward 5), but the file's error contract (`{success: false, message}`) is consumed by `newsletter/route.ts:39-42` which currently silently continues on failure. Confirm with owner whether a SendGrid timeout should be treated as success (current implicit) or surfaced as user-visible error before changing the call.
2. **`adopt/page.tsx:111` raw `JSON.stringify(offerSchema)` vs `toJsonLd()` (C14)** — fix is one line, but check whether `offerSchema` is intentionally serialized differently (e.g. preserving `undefined` keys) for an offer-specific schema.org tweak. If `toJsonLd()` strips fields that this page relies on, swap will silently regress SEO.

Either extend the hook (`buildEndpoint?: (locale) => string`, `onError?: (msg) => void`) or leave newsletter as-is. Owner intent: is locale-prefixed routing a deliberate i18n decision or accidental? If accidental, drop the prefix and adopt the hook for free.
