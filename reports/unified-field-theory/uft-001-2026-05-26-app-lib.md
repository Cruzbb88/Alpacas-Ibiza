## L3 — Overlap Detection

### Full Duplications (>80% similar)

**FD-1: Inline email HTML in contact + commission routes**
Both routes build structurally identical HTML:
- `<div style="font-family:sans-serif;max-width:600px">` wrapper
- `<h2 style="color:#556B2F">` header
- `<table>` with Name/Email rows + `style="background:#f9f9f9"` on alternating row
- `<div style="background:#f5f5dc;border-radius:8px">` content block
- `<p style="color:#888;font-size:12px">` footer line

`lib/email-templates.ts` already has `emailLayout()` and `BRAND` constants but these two routes were not migrated to use them.

**FD-2: Client form component body (contact-form.tsx vs commission-form.tsx)**
Both are character-for-character identical except:
- Field set (`subject`+`message` vs `description`)
- API endpoint (`/api/contact` vs `/api/commission`)
- trackConversion call
- Success emoji (✅ vs ✨)
Same state machine, same handleChange, same CSS classes, same TurnstileWidget integration, same button structure.

**FD-3: Fallback owner email inline in routes**
`process.env.CONTACT_EMAIL || 'info@alpacasibiza.com'` or `?? 'info@alpacasibiza.com'` appears in 7 places. `lib/mailer.ts` line 4 already owns the canonical default (`DEFAULT_TO`) but routes re-derive it locally — including as `replyTo` in fareharbor-webhook (x2), reminder, review-request.

### Partial Overlaps (40-80% similar)

**PO-1: Secret-gated route auth (reminder + review-request vs fareharbor-webhook vs owner-digest)**
reminder and review-request share the same pattern: read `FAREHARBOR_WEBHOOK_SECRET`, check header `x-webhook-secret` with `safeEqual()`, return 401. But they differ from fareharbor-webhook in one key way: they are **fail-open** (auth skipped if secret unset) while fareharbor-webhook is fail-closed. owner-digest further diverges: different env var (`CRON_SECRET`), different header (`Authorization: Bearer`), plus query-param fallback. These are related but each has a legitimate semantic reason to differ — a shared `requireSecret()` helper would need to encode both fail-open and fail-closed modes.

**PO-2: FareHarbor shortname resolution**
`lib/config.ts` is already the canonical source for client-side embed URLs, but `app/api/availability/route.ts:7` and `app/api/owner-digest/route.ts:32` each declare `const shortname = process.env.FAREHARBOR_SHORTNAME || 'alpacasibiza'` independently. The server-side var is `FAREHARBOR_SHORTNAME`; config.ts uses `NEXT_PUBLIC_FAREHARBOR_SHORTNAME` — different env vars, intentional split, but the fallback string is duplicated.

**PO-3: Date range computation**
availability, owner-digest, and analytics/data each build `startDate + N days` → `YYYY-MM-DD` strings. Minor copy-paste — no current divergence bugs but a future "30 days" change would need to be made in 3 places.

**PO-4: i18n accessor naming (cosmetic)**
Components use `const tr = t(locale)` (header, footer, booking-section, etc.) or `const translate = t(locale)` (newsletter-form, contact page, about page). Both call the same function. No logic difference. Cosmetic inconsistency only.

### False Positives

- **Image rendering**: Only 2 pages use `next/image` (experience detail pages). All other pages compose `<img>`-free markup or use components. No divergence pattern.
- **Error handling try/catch shape**: Routes that call `sendEmail` wrap in `try/catch` and return 500. Routes that call external APIs do the same. Minor wording difference (`'Send failed'` vs `'Internal server error'`) but not a duplication risk.
- **Currency formatting**: `product-card.tsx` uses `.toFixed(2)` for shop items (correct — two decimals for prices), owner-digest uses `.toFixed(0)` for revenue totals (correct — rounded). Shop pages use hardcoded string literals (`'€45'`) because those are fixture data, not computed. These are intentional, not overlap.

## L4 — Unification Proposals

### Proposal 1: Migrate contact + commission email HTML to emailLayout()
**Pattern name:** Inline owner-notification email HTML
**Where it appears:**
- `app/api/contact/route.ts:35-49`
- `app/api/commission/route.ts:34-47`
**Proposed abstraction:** Add `contactEmailHtml(fields)` and `commissionEmailHtml(fields)` to `lib/email-templates.ts`, using existing `emailLayout()` + `BRAND` constants. The table-row pattern (Name, Email + alternating `#f9f9f9`) is already implicit in emailLayout's structure.
**Migration cost:** S (< 1h — two simple function additions + route import swap)
**Risk:** 2/5 — email content is low-stakes; XSS safety preserved via escapeHtml at call site; only risk is accidentally changing the HTML structure
**Recommendation:** UNIFY — the infrastructure (emailLayout, BRAND) already exists. Contact and commission routes are simply not using it.

---

### Proposal 2: Centralize fallback owner email to lib/mailer.ts export
**Pattern name:** CONTACT_EMAIL fallback address
**Where it appears:**
- `app/api/contact/route.ts:6` (module-level const)
- `app/api/commission/route.ts:6` (module-level const)
- `app/api/fareharbor-webhook/route.ts:161,179` (inline in two sendEmail calls)
- `app/api/reminder/route.ts:64`
- `app/api/review-request/route.ts:48`
- `app/api/owner-digest/route.ts:29`
- `lib/mailer.ts:4` (already the canonical default for `to`)
**Proposed abstraction:** Export `OWNER_EMAIL` from `lib/mailer.ts` (already computed as `DEFAULT_TO`). Routes replace their local `process.env.CONTACT_EMAIL || 'info@alpacasibiza.com'` with `import { OWNER_EMAIL } from '@/lib/mailer'`.
**Migration cost:** S (< 1h — global find-replace + export one constant)
**Risk:** 1/5 — pure constant extraction; no logic change
**Recommendation:** UNIFY — single source of truth for the fallback address, which is a business constant.

---

### Proposal 3: Abstract shared-secret route guard into lib/secrets.ts
**Pattern name:** x-webhook-secret header guard
**Where it appears:**
- `app/api/fareharbor-webhook/route.ts:64-76` (fail-CLOSED)
- `app/api/reminder/route.ts:17-24` (fail-OPEN)
- `app/api/review-request/route.ts:13-20` (fail-OPEN)
- `app/api/owner-digest/route.ts:18-26` (different header + query-param fallback, fail-CLOSED)
**Proposed abstraction:** `lib/secrets.ts` exports `checkWebhookSecret(request, envVar, opts: { failClosed?: boolean }): NextResponse | null`. Returns a 401/503 response if auth fails, or `null` if OK. Each route calls it at the top: `const authErr = checkWebhookSecret(request, 'FAREHARBOR_WEBHOOK_SECRET', { failClosed: true }); if (authErr) return authErr`.
**Migration cost:** M (2-3h — needs careful handling of the two auth modes + the bearer-token variant in owner-digest)
**Risk:** 3/5 — auth code; subtle differences (fail-open vs fail-closed) must be preserved exactly. owner-digest bearer-token path complicates the API.
**Recommendation:** PARTIALLY UNIFY — unify reminder + review-request (identical pattern) first. fareharbor-webhook and owner-digest have enough divergence to stay separate or opt-in only after the simpler pair proves out.

---

### Proposal 4: Add FareHarbor server-side shortname to lib/config.ts
**Pattern name:** FareHarbor shortname resolution
**Where it appears:**
- `lib/config.ts:34` (NEXT_PUBLIC_FAREHARBOR_SHORTNAME — client-side)
- `app/api/availability/route.ts:7` (FAREHARBOR_SHORTNAME — server-side)
- `app/api/owner-digest/route.ts:32` (FAREHARBOR_SHORTNAME — server-side)
**Proposed abstraction:** Add `export const FAREHARBOR_SHORTNAME_SERVER = process.env.FAREHARBOR_SHORTNAME || 'alpacasibiza'` to `lib/config.ts`. Routes import it. Note: `lib/config.ts` already warns on missing `NEXT_PUBLIC_FAREHARBOR_SHORTNAME` in prod — the same guard should cover the server-side var.
**Migration cost:** S (< 30 min — one export + two import swaps)
**Risk:** 1/5 — pure constant extraction
**Recommendation:** UNIFY — the fallback string `'alpacasibiza'` appearing in 3 places is a single-point-of-failure for future renames.

---

### Proposal 5: Extract shared client form component base
**Pattern name:** Turnstile-gated form submit state machine
**Where it appears:**
- `components/contact-form.tsx` (3 fields: name, email, subject, message)
- `components/commission-form.tsx` (3 fields: name, email, description)
- `components/newsletter-form.tsx` (1 field: email)
**Proposed abstraction:** A `useTurnstileForm<T>` hook or a `<BaseForm>` render-prop component that owns `status`, `captchaToken`, `handleChange`, `handleSubmit(endpoint, onSuccess)`. Individual forms provide field definitions and success/error UI variants.
**Migration cost:** L (3-5h — hook extraction + refactor 3 components + regression test all 3 forms)
**Risk:** 4/5 — these are user-facing form submission paths; any regression in captcha token threading or status transitions breaks conversion. newsletter-form's dual-send pattern is also different enough that the abstraction boundary is non-obvious.
**Recommendation:** MONITOR — the duplication exists but the forms are small and infrequently changed. The risk/reward ratio only flips if a 4th form is added or if the captcha widget changes API. Do not unify proactively.

## CAN'T DO WITHOUT HELP — What Runtime / Historical Data Would Confirm These

1. **Git churn frequency on contact/commission routes** — if these routes have been edited together 3+ times in git history, that's a signal the inline HTML is already causing drift and proposal #2 has higher urgency. `git log --follow -p app/api/contact/route.ts` would show this.
2. **Error rate on reminder vs review-request vs fareharbor-webhook** — if the fail-open routes (reminder, review-request) are called in production, telemetry would confirm whether the auth-guard divergence is causing real 401 noise or is theoretical.
3. **4th form incoming?** — if the roadmap has a new form (gift inquiry, farm visit request), the cost/benefit of extracting `useTurnstileForm` flips immediately. Check PLAN.md / OWNER_INPUT_NEEDED.md for pending form requirements before deciding on proposal #5.
4. **Shop price data source** — shop pages use hardcoded `'€45'` strings. If prices are owner-managed, they need a data layer (lib/data or CMS), not a unification. This is a separate concern from the currency formatting overlap, but worth flagging: if prices ever need to change, there's no single place to update them.
