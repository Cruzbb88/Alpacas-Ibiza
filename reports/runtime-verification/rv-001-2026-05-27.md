## Findings

### ⚠️ /feed.xml returns HTML, not RSS

`/feed.xml` returns a full Next.js HTML page (127 KB, `Content-Type: text/html`) with the `[locale]` catch-all route treating "feed.xml" as a locale string.

The actual RSS feed lives at `/journal/rss.xml` (`app/journal/rss.xml/route.ts`) and works correctly — returns valid RSS 2.0 XML with real posts.

Impact: Any RSS reader subscribed to `/feed.xml` gets a broken feed. The sitemap and any `<link rel="alternate" type="application/rss+xml">` pointing to `/feed.xml` would be wrong.

Fix: Either add a redirect `{ source: '/feed.xml', destination: '/journal/rss.xml', permanent: true }` in `next.config.mjs`, or add a dedicated `app/feed.xml/route.ts` that calls the same RSS builder.

Also note: `/en/journal/rss.xml` similarly returns HTML — the route file is at `app/journal/rss.xml/` (no locale prefix), which is correct but means the locale-prefixed path silently serves the wrong content.

### ⚠️ middleware deprecation warning

`The "middleware" file convention is deprecated. Please use "proxy" instead.` — fires on every boot. Not blocking, but will become an error in a future Next.js version.

### Journal page has empty `<title>`

`/en/journal` has an empty `<title>` tag. There are no live journal posts in `lib/data/journal.ts` (all are draft/scheduled), so the page serves the "coming soon" empty state — but the `<title>` tag is empty rather than a fallback like "Journal | Alpacas Ibiza". This is an SEO issue if the journal stays dark at launch.

### /feed.xml locale-catch behavior is a 200, not a 404

Because `[locale]` catches "feed.xml" as a valid param and renders a page, the server returns 200 with HTML. This is harder to detect in automated checks than a 404 would be. Worth logging or middleware-blocking unknown locale values.

### Probe: /en/about exists (200)

The old-site redirects point many Dutch paths to `/en/about`, and the route serves content. Not broken — just confirming the redirect targets land.
